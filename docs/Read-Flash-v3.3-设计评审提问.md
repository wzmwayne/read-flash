## A 类 · 阻断问题

### A1 阅读界面是否解析组件语法？

- **位置**：§2.2、§2.5、§4.1、§6.3、§16.5
- **问题**：§2.2 说正文区"支持标题、按钮、单选、多选、换页符"；§4.1 的组件表没有作用域限制；§6.3/§6.4 的 `---`、`#` 又明确用于正文。但 §2.5 与 §16.5 断言"阅读界面正文区没有可交互的按钮组件（只有正文）"。
  - 一个普通 TXT 里出现 `[打开]`、`~~~`、`(+)`、行首 `<`、`# 标题` 时，是渲染成组件还是原样文本？
  - 若解析：阅读界面也存在热区，§16.5 "左右 1/2 点击不会与组件冲突"的论证不成立（§2.5 特意说明阅读界面"不需要为组件留出中间点击区"）。
  - 若不解析：`---` 换页符在阅读界面是否仍生效？§4.5 的"行首 `<` 返回"是否在阅读界面生效（正文以 `<` 开头会变成返回键）？
- **建议**：新增一节"语法作用域表"，逐条列出每种语法在〔阅读书 / 内置书〕下是"解析为组件"还是"字面文本"，并据结论修订 §16.5。

`→ 结论：`
阅读界面中“正文”部分遵循部分（分段（换页）、标题等必要）
### A2 `canPrev` 判定与进度模型在长行跨页时失效

- **位置**：§7.4、§8.3、§16.2、§16.6、I9
- **问题**：`canPrev = !(firstSourceLine == 1)`。当同一个源文件行跨越多页时（§8.3 明确承认这种情形），第 2…N 页的 `firstSourceLine` 仍是该行行号；若该行是文件第 1 行，则**所有后续页的 `<` 都显示为不可用**，而它们并不是第一页 —— 用户无法往回翻，直接违反 §16.6 "不会出现不可用但点了有效 / 可用但点了没反应"。
  - 极端例子：5MB 无 `\n` 的单行 TXT → 每一页 `firstSourceLine` 都是 1 → `<` 永远不可用；`.rfprog` 永远记录 1 → 书库进度恒为 0%，重开永远回到顶部，`>` 也无法通过进度恢复。
  - §8.3 "偏移几行不影响体验"的前提是"行 ≈ 显示行"，对无换行或超长行文件不成立。
- **建议**：`canPrev` 改为基于"本页起点是否为文件绝对起点"（例如 `firstByteOffset > 0`）判定；PageState 需携带 `firstByteOffset`；并明确超长行的进度语义（是否允许 `sourceLine` 之外的恢复锚点）。

`→ 结论：`
通过行+行字节来计算阅读进度。
### A3 PageState 缺少"行内断点"

- **位置**：§7.1、§7.2、§16.1
- **问题**：§7.2 说 `Filled` 时"从末行续排位置开始"，§16.1 说"下一页从 `(lastSourceLine, lastByteOffset)` 起始"，但 §7.1 的 `PageState` 只有 `firstSourceLine / lastSourceLine / displayLineCount / terminateReason`，**没有 `lastByteOffset`**。
  - 下一页是"用 `firstSourceLine` 重排本页再继续"（每次翻页都重做 O(V) 排版，内存仍满足 I2），还是"缓存行内断点"（需扩充 PageState）？
  - 若是前者，需明确：下一页的结果必须与"从 `firstSourceLine` 重新排版"逐字节一致，否则会破坏"不重不漏"。
- **建议**：二选一并写入 §7.1/§7.2；若选重排，需说明 `locate()` 与重排的成本仍在 §14 的"翻页 < 10ms"内。

`→ 结论：`
实时渲染，不要提前渲染。
### A4 "换行分隔二进制"与二进制字段的定界冲突

- **位置**：§1.1 P3、§5.2、§9.1–§9.3
- **问题**：每行是定长二进制字段（8B/4B 小端），其字节序列**完全可能包含 `0x0A`**。例如 `sourceLine = 0x0A000000` 的字节序列是 `00 00 00 0A`；8 字节魔数同样可能含 `0x0A`。
  - 按 `\n` 分行解析 → 字段被截断、行数错位；
  - 按定长读取 → "换行分隔"的表述失去意义，需要额外约定"每条记录 = N 字节数据 + 1 字节 `0x0A`"，且读取时必须校验该分隔符。
  - 同时 §1.1 P3 宣称"文本可调试"，含 `0x0A` 的二进制值和二进制魔数都不可读。
- **建议**：明确读取契约（推荐：定长记录 + 必须为 `0x0A` 的记录尾 + 记录内允许任意字节），或在格式层避免歧义（十六进制 ASCII 编码，牺牲体积换可调试性）。

`→ 结论：`
修改，不一定定长，但是以换行符作为分割。
### A5 终止原因优先级、EOF 判定与空尾页

- **位置**：§7.1、§7.2、§7.4、§15
- **问题**：
  1. 一页**恰好排满**视口且文件到此结束：`terminateReason` = `Filled` 还是 `EOF`？若为 `Filled`，则 `canNext = true`，点下一页得到空页 —— 违反 §16.6。判定 EOF 是否必须向前预读 1 行/1 字节？
  2. 文件结尾是 `---` 时，末页 `terminateReason = Forced` → `canNext = true`，但下一页无内容；§15 说"连续 `---` 第一个终止当前页，后续空页忽略"，那**单个尾随 `---`** 是否产生一个空白页？空尾页与 §15 的"忽略"如何统一？
  3. `Forced` 与 `EOF` 同时成立时的优先级未定义。
  4. `displayLineCount = 0` 的页（例如文件以 `---` 开头），`firstSourceLine` / `lastSourceLine` 取什么值？"本页首显示行的源文件行号"在零显示行时无定义。
- **建议**：定义 `terminateReason` 的判定优先级与"空页不算页"的规则，并规定 `canNext` 只在"确有能力继续"时为真。

`→ 结论：`
阅读中的换页符指的是当前页面从换页符上方那一行到正文底部都是渲染空行，其他界面不允许换页符解析。
### A6 K 的取值公式与"索引 ≤ 24KB"自相矛盾

- **位置**：§5.2、§14、§15
- **问题**：索引字节数 = `ceil(L/K) × 9B`，而 `K = 2^ceil(log2(L/4096))` ⇒ 条目数 ∈ (2048, 4096]（未触顶时）。
  - 实际范围是 **(18KB, 36KB]**，不是"约 24KB 上限"。反例：`L = 8,388,608` → `K = 2048` → 4096 条 → 36,864 B。
  - 当 `L > 2.68×10⁸` 时 `K` 顶到 65536，索引随行数**线性增长**（`L = 10⁹` → 15,259 条 → 137KB），与"与文件行数解耦"矛盾。
  - `L = 0` 时 `log2(0)` 无定义；`L < 4096` 时 `2^ceil(log2(L/4096)) < 1`，是分数 —— 需明确"先 `max(1, ·)` 再 clamp"还是"clamp 直接吸收"。
  - `index1[j] = start(j×K + 1)` 在 `j×K + 1 > L` 时 `start()` 无定义；条目数应写为 `L > 0 ? ceil(L/K) : 0`。
  - `K` 必须是 2 的幂（因为用 `>> log2(K)` 与 `& (K-1)`），clamp 到 256/65536 恰好保持幂次，但公式本身要说明。
- **建议**：给出 K 的分段定义、条目数公式、索引字节数上界；把"24KB"改成真实上界或改为"≤ 36KB"。
不限制但是内建超长整数高精度运算、二进制解析模块
`→ 结论：`

### A7 `.rfidx` 没有校验和，但要求"索引损坏 → 删除重建"

- **位置**：§5.2、§15
- **问题**：索引头部只有 魔数 / L / S / 采样哈希 / K / index1[]。若某个 `index1[j]` 被写坏（磁盘错误、写到一半被杀），**没有任何字段能检测到**；采样哈希校验的是**源文件**，不是索引本身。

`→ 结论：`
可以

### A16 上一页的 V×3 回溯窗口不保证"不重不漏"

- **位置**：§7.3、§16.1、§4.1、§4.3（依赖 A1 的结论）
- **问题**：§7.3 "往前估 V×3 行" 的有效前提是"每个源文件行至少产生 1 个显示行"。但 §4.1 中有**不产生显示行**的行：`~~~`、`/~~~`；§6.3 的 `---` 也不产生显示行。
  - 若阅读界面解析 `~~~`（见 A1），一段连续的 `~~~` 可以让一页覆盖任意多源文件行，`V×3` 的回溯窗口不足 → 上一页会**跳过内容**，违反 §16.1。
  - 若阅读界面不解析 `~~~`，则只有 `---` 不产生显示行，而 `---` 会立即终止页面，`V×3` 恰好够用 —— 该问题因此依赖 A1。
- **建议**：改为"倍增回溯"（从 V 行开始翻倍直到覆盖一页所需显示行）或"每页记录源行跨度上界"，并在 §16.1 补充证明。

`→ 结论：【自决】`
- 改用"按渲染行回溯"，并把不变量作为证明前提：**R1：阅读书内每个源行至少产生 1 个渲染行**（`---` 依 A5 填空白至页底、`#` 标题占 1–2 行、空行也占 1 行）⇒ 每页覆盖的源行数 ≤ V + 1。
- 算法：回溯起点 `B = max(1, firstSourceLine − (V + 2))`，从 B 起实时排版并累积渲染行，取"结束于当前页首锚点之前的最后 V 行"作为上一页；窗口内渲染行 ≥ V + 1，必然能取满一页 ⇒ 不重不漏可证。
- 若未来让阅读书解析不产生渲染行的语法（如 `~~~`），必须同步改为倍增回溯；此前提写入 §7.3。

### B14 单击判定的细节
- **位置**：§11.2
- UP 丢失（手指划出屏幕、来电、系统手势抢占）如何取消？"移动距离 < 10px"是欧氏距离还是分轴？
- `10px` 是物理像素还是 dp/dip（3x 屏上 10px ≈ 3.3dp，几乎无法容忍抖动）？
- 多指同时按下如何处理？是否需要"按下高亮"视觉反馈（全文没有按压态规范）？

`→ 结论：【自决】`
- 单击 = DOWN 后 300ms 内 UP，且 `max(|dx|,|dy|) < 10`（单位：**逻辑像素 dp**，非物理 px，避免高 DPI 屏抖动误判）。
- 取消条件（恢复视觉、不触发）：超时、位移超限、收到 CANCEL、触点离开窗口、出现第 2 个触点、应用退到后台。
- 多指：仅第一个 DOWN 有效，出现第二指即取消。
- 视觉反馈：DOWN 立即切换为焦点配色（B4），UP 恢复并触发对应交互 ID 的操作；拖出热区后回到热区内仍算单击，只要满足 300ms/10dp。

`→ 结论：【自决】`
- `[保存]` 后 settingsSaved 更新，当前页立即按新参数重排（排版不持久化，重排 O(V)），保持页首锚点 `(sourceLine, lineOffset)`。
- 未保存返回：settingsCurrent = settingsSaved 并重排。
- 示例文本 = 编译期固定的 UTF-8 字面量（约 2 屏），必须包含：中文段落、英文单词与数字、全角标点、三档标题各一、空行、一条超出屏宽的长行；**不含** `---`（生成式书不解析换页符，见 A5）与交互组件语法。

### B19 字号变化后的恢复语义
- **位置**：§8.4、§16.2
- 恢复是"`sourceLine` 出现在页内任意位置即可"还是"必须是页首行"？文档只说"从该行行首排版"，需要明确验收标准。

`→ 结论：【自决】`
- 恢复 = 以 `(sourceLine, lineOffset)`（行 + 行内字节偏移，依 A2 用户结论）为**页首锚点**实时排版，该锚点即页面第一个渲染行的起始字节。
- 不要求锚点落在原页面的同一屏位置（字号/边距/尺寸变化必然改变分页）。
- 验收标准：恢复后第一个渲染行的首字节偏移 == `.progress` 记录的偏移；字号变化前后定位到同一源字节。

## C 类 · 存储与解析

### C1 魔数与版本的拆分
- **位置**：§5.2、§9.1、§9.2
- "魔数+版本 8B"的具体值？如何拆分（4B 魔数 + 4B 版本？7B + 1B？）？版本不匹配时按"损坏"处理（索引重建 / 进度重置 / 设置回默认）吗？

`→ 结论：【自决】`
- 依 A4 用户结论（以换行符分割、不一定定长），存储文件整体改为 **ASCII 行文本**：魔数 = 6 个 ASCII 字符 + 3 位十进制版本，独占一行。
- `.rfidx` → `RFIDX001`；`.progress` → `RFPROG001`；全局配置 → `RFSET001`；每书 `.config` → `RFBOOK001`。
- 版本不匹配一律按损坏处理：索引重建、进度重置为起点、配置回默认；坏文件改名为 `*.bad` 保留一份。

### C2 校验和算法与覆盖范围
- **位置**：§9.1、§9.2
- 4B 校验和是 CRC32 吗（多项式、初值、是否反射、末尾异或）？还是 Adler-32 / 自定义累加？
- 覆盖范围是"前 N 行的字节"还是"除校验行外的全部字节"？是否包含各行尾的 `\n`？

`→ 结论：【自决】`
- 统一采用 **CRC-32/ISO-HDLC**（多项式 0xEDB88320、初值 0xFFFFFFFF、输入输出反射、末尾异或 0xFFFFFFFF，即 zlib `crc32`），以 8 位大写十六进制写在文件**最后一行**。
- 覆盖范围 = 文件首字节至校验行之前（**包含**各行尾 `\n`，不含校验行自身）。
- 四个存储文件（`.rfidx` / `.progress` / 全局配置 / `.config`）统一使用。

### C3 采样哈希算法
- **位置**：§5.2、§15
- "文件采样哈希 8B"的采样策略必须完全确定（采样哪些区域、每区多少字节、步长多少、小文件是否退化为全文件哈希），否则跨版本/跨设备对"索引是否有效"的判断不一致。8B 的碰撞概率是否可接受？

`→ 结论：【自决】`
- 取消"8B 采样哈希"，改为三元组：`S` = `book` 文件字节数；`H1` = 首 `min(S,4096)` 字节的 CRC32；`H2` = 尾 `min(S,4096)` 字节的 CRC32。
- 三者任一与当前文件不符即重建索引；打开时最多读 8KB，满足"二次打开 < 10ms"。
- 采样窗口固定 4096 字节（`S ≤ 4096` 时 `H1 = H2`），跨设备、跨版本结果完全一致。

### C4 `L` 的宽度前后不一致
- **位置**：§5.2 行2（8B）vs §7.1 / §8.1（`uint32`，4B）
- 以哪个为准？如果 `uint32` 是刻意的上限，索引里为何用 8B？（`S` 也用 8B，说明支持 > 4GB 文件，却不支持 > 42 亿行。）

`→ 结论：【自决】`
- 统一为 **uint64 无符号**（行号、字节偏移、字节数、时间戳），文本 16 位大写十六进制。
- 不再出现 4B/8B 混用；行号上限 2^64−1，与 `S` 的宽度一致。

### C5 字节序、符号与对齐
- **位置**：§9.4
- 已声明小端；那么所有字段都是无符号整数吗？8B 是 `uint64` 还是两个 `uint32`？是否存在填充字节？这些都要写死，否则跨平台实现不一致。
- `timestamp`（§8.1，8B）的单位与时钟源未定义：Unix 秒？毫秒？还是上电后的单调时钟计数（§12.2 的 PAL 里根本没有时钟接口）？

`→ 结论：【自决】`
- v3.4 存储文件为 ASCII 十六进制行文本，**与端序无关**；§9.4 的"统一小端"仅保留给未来可能引入的二进制块。
- 所有数值无符号，禁止 `+`/`-`/空格，前导零必须补齐到定宽。
- `timestamp` = **Unix 秒**（uint64），由 `pal_now_unix()` 提供；点击判定的 300ms 与滚动渲染的 0.5s 使用**单调时钟** `pal_ticks_ms()`（PAL 需补，见 D1）。

### C6 索引加载时的自校验
- **位置**：§5.2、§15
- 除魔数与采样哈希外，是否校验：`K ∈ {256…65536}` 且为 2 的幂、`index1` 严格递增、`index1[0] == 0`、末项 `< S`、条数 `== ceil(L/K)`？不通过时是否直接重建？

`→ 结论：【自决】`
- 加载索引时必须全部校验，任一失败即删除重建（重建前改名 `*.bad`）：
  1. 魔数与版本；2. CRC32；3. `K` 为 2 的幂且 `256 ≤ K ≤ 2^24`；4. 条目数 `N == (L > 0 ? ceil(L/K) : 0)`；5. `index1[0] == 0`；6. `index1` 严格递增；7. `index1[N−1] < S`；8. `S/H1/H2` 与当前 `book` 文件一致。

### C7 哈希采样时机与"二次打开 < 10ms"
- **位置**：§14、§15
- 每次打开都要读采样区并计算哈希吗？采样分散在 5MB 各处时，二次打开 < 10ms 是否仍成立？是否只在 `size` / `mtime` 变化时重算（§12.2 的 PAL 没有 `mtime` 接口）？

`→ 结论：【自决】`
- 每次打开都重算 `S/H1/H2`（≤ 8KB 读取 + 两次 CRC32，远小于 10ms）；**不使用 mtime**（PAL 也不提供）。
- 索引头部存有同一组 `S/H1/H2`，命中则直接使用索引，跳过扫描。

### C8 进度写入的原子性
- **位置**：§8.2、§9.1
- "翻页即写、无节流"下，写入是"临时文件 + rename"还是原地覆盖？掉电/进程被杀导致半截文件时由校验和兜底"从头开始"——**这会让用户进度被清零**，是否有"写入失败保留旧值"的约定？

`→ 结论：【自决】`
- 所有落盘统一 **"临时文件 + rename" 原子替换**：PAL 提供 `pal_file_write_atomic(path, buf, len)`（写 `path.tmp` → 关闭 → rename 覆盖）。
- 不做 fsync（低端设备功耗与寿命优先）：掉电最多丢失**最后一次翻页**，旧文件在被替换前始终完整，因此不会出现"校验失败 → 进度清零"。
- 写入失败时保留旧文件，并在调试页计数。

### C9 写盘频率与闪存寿命
- **位置**：§8.2、§14
- 快速连点下一页（每秒 5 次）就是每秒 5 次写入/fsync？是否需要写合并，同时保持"翻页即保存"的语义（例如崩溃最多丢 N 页）？§8.2 明确说"无节流、无定时器"，需要给出理由或修订。

`→ 结论：【自决】`
- 保留"翻页即保存、无节流"（用户未推翻）；每次写入 ≤ 64 字节且为原子替换、无 fsync，闪存代价可接受。
- 若实测写入放大不可接受，允许引入"最多 8 次/秒的合并写"，但必须同时满足：崩溃最多丢失 ≤ 1 秒的翻页。

### C10 源文件变化后的进度处理
- **位置**：§15、§8
- 哈希不匹配 → 索引失效重建，但 `.rfprog` 里的行号在新文件里可能已越界（旧 240 万行 → 新 100 行）。是 clamp 到末行、重置为 1，还是按百分比缩放？（`.rfprog` 里没有源文件哈希，无法判断"同一本书换了内容"。）

`→ 结论：【自决】`
- 依 A10 用户结论，正文位于应用私有目录 `<app_data>/book/<ID>/book`，导入后外部不可修改 → "源文件被改"的常规场景消失，只保留防御规则。
- 索引 `S/H1/H2` 不符 → 重建；重建后若进度 `sourceLine > L` 或 `lineOffset` 越界 → clamp 到末行末字节；`L == 0` → 进度重置为 `(0,0)`。

### C11 附属文件的存放位置与命名
- **位置**：§12.2、§9
- `.rfidx` / `.rfprog` / `.rfset` 放在源文件同目录（可能只读、可能污染用户目录、可能被同步？）还是应用私有目录？命名规则？PAL 需要补哪些接口（见 D1）？

`→ 结论：【自决】`（目录与 ID 规则来自 A10 用户结论）
```
<app_data>/config               全局配置（RFSET001：字号/行距/四向边距）
<app_data>/book/<ID>/book       正文（导入时复制，此后只读）
<app_data>/book/<ID>/.config    书信息（RFBOOK001：书名、目录、统计）
<app_data>/book/<ID>/.rfidx     索引（RFIDX001）
<app_data>/book/<ID>/.progress  进度（RFPROG001）
```
- `<ID>` = 8 位大写十六进制：前 6 位取 `book` 文件 CRC32 的高 3 字节，后 2 位为冲突序号（初始 `00`，冲突则 `01`…`FF`；用尽后改用低 3 字节重算）。
- 进度独立成文件而不并入 `.config`：目录（TOC）可能很大，而进度要"翻页即写"。
- PAL 需增 `pal_app_data_dir()`；`config` 与 `book/` 名字固定。

### C12 空文件的存储表现
- **位置**：§15、§8.1、§5.2
- `L = 0` 时 `.rfidx` 如何写（`K` 取多少、`index1` 为空还是含一项）？`.rfprog` 的 `sourceLine` 与 `totalLines` 取 0 还是 1？

`→ 结论：【自决】`
- 空文件（`S = 0`，`L = 0`）：索引只写头部，`K = 256`，条目数 `N = 0`（无 `index1` 行）；`.config` 的目录为空。
- 进度写 `(sourceLine = 0, lineOffset = 0)`；书库显示 `0%`；打开显示空白页，两个翻页键均不可用。

### C13 删除书时的附属文件清理
- **位置**：§2.6
- 删除源文件时是否一并删除 `.rfidx` / `.rfprog`？删除失败如何回滚/提示？是否受 A15（无确认）影响？

`→ 结论：【自决】`
- 删除 = 删除整个 `<app_data>/book/<ID>` 目录（正文、`.config`、`.rfidx`、`.progress` 一并删除）。
- 实现：先 rename 到 `<app_data>/trash/<ID>` 再递归删除；失败可重命名回来并提示。
- 必须经 A15 的**提示框书**二次确认（`[删除]` 用危险色 + 确定/取消）。

### D2 线程与阻塞模型
- **位置**：§12.2、§14
- 首次打开 5MB < 100ms 若在 UI 线程执行，是否可接受（掉帧但无 ANR）？索引重建能否取消？
- PAL 没有线程接口 → 请显式声明"单线程模型"与"单次最长阻塞时间"预算，否则 §14 的指标无法验收。

`→ 结论：【自决】`
- v1 为**单线程事件循环**：`poll_event → 状态更新 → 脏区重绘 → 上屏`，PAL 不提供线程接口。
- 允许的阻塞：导入/重建索引（≤ 300ms/5MB，超时则分片执行，并在提示框书显示"正在建立索引…"）。
- 禁止在渲染路径内做文件 I/O；单帧渲染预算 ≤ 10ms。

### D3 尺寸变化 / 旋转 / 分屏
- **位置**：全文缺失
- 横竖屏切换、窗口 resize、iOS 分屏与安全区如何处理？V 重新计算后，当前页是按 `firstSourceLine` 重排、还是保持"同一屏内容"？未保存的 PageState 怎么办？

`→ 结论：【自决】`
- 尺寸/DPI/安全区变化（旋转、分屏、resize）时：重建整数网格（A12）→ 重算边距（只会变大）→ 重算 V 与顶栏/底栏位置 → 当前页按页首锚点 `(sourceLine, lineOffset)` **实时重排**。
- 阅读书同时把新锚点写回 `.progress`；未保存的 PageState 直接丢弃（I4：排版不持久化）。

### D4 渲染路径与帧率
- **位置**：§3.3、§12.3、§14
- §3.3 描述的是**软件光栅化**（CPU 帧缓冲 + `memset` + 贴字形），§12.3 却说后端是 EGL + OpenGL ES。两者关系是"CPU 合成到一张纹理再上传"还是"直接用 GPU 画四边形/字形图集"？
- 若是前者，低端 ARM 上全屏清屏 + 上传的带宽/耗时是否仍满足"翻页 < 10ms"？是否改为脏矩形重绘？目标帧率与单帧预算是多少？

`→ 结论：【自决】`
- 渲染路径：CPU 软件渲染到 **RGB565 帧缓冲**（尺寸 = 窗口物理像素），按**网格行脏区重绘**（记录本帧需重绘的网格行区间，最多整屏）；上屏用 GLES `glTexSubImage2D` 只上传脏区。
- 翻页/滚动渲染时目标单帧 ≤ 10ms；静止时 0 帧（不空转重绘）。
- 帧缓冲由渲染后端持有，计入应用峰值内存、不计入"常驻"（与 E2 调试显示口径一致）。

### D5 iOS 渲染后端已弃用
- **位置**：§12.3、§17
- OpenGL ES 自 iOS 12 起被 Apple 标记为 deprecated，EAGL 亦不再演进（参见 Apple 归档文档与 WWDC19 "Bringing OpenGL Apps to Metal"：[文档](https://developer.apple.com/library/archive/documentation/OpenGLES/Conceptual/OpenGLESHardwarePlatformGuide_iOS/RevisionHistory.html)、[WWDC19](https://developer.apple.com/br/videos/play/wwdc2019/611/)）。§17 又写"平台 iOS 12+"。
- 是否接受弃用风险（新系统版本、Apple Silicon 模拟器、未来移除），还是 iOS 侧改用 Metal、仅 Android 用 GLES？

`→ 结论：【自决】`
- v3.4 保留 **GLES 2.0** 作为 Android/iOS 共同后端，但把渲染后端抽象为 `render_backend` 接口（清屏 / 纹理上传 / 绘制三角形三类调用），iOS 侧后续可整体替换为 Metal。
- 文档显式记录：OpenGL ES 在 iOS 12+ 已弃用、未来可能被移除；若上架受阻则以 Metal 后端替换，Android 4.4+ 无此风险。

### D6 字体许可证的推论需要法律确认
- **位置**：§13
- 文档称"GPL v2：项目以 GPL 兼容许可证发布可静态嵌入；**否则运行时从独立文件加载**，About 页面注明"。这个推论把"静态嵌入"与"运行时加载"当成 GPL 的义务分界，但 GPL v2 **不区分**二者：只要**分发字体文件本身**（无论内嵌还是独立文件），就触发 GPL 的分发义务（附许可证全文、提供对应源码或书面要约）。运行时加载能规避的是"应用程序与字体构成组合/衍生作品"的争议，不是分发义务。
- 请给出文泉驿正黑具体发行版本的许可证条款出处（是否附带"字体嵌入例外"，可参考其[发行规格文件](https://wenq.org/release/zenhei/wqy-zenhei-fonts.spec)），或改用 OFL 字体以彻底消除歧义；并明确 About 页需要列出的合规信息。

`→ 结论：【自决】`
- 优先改用 **OFL-1.1 字体**（如 Noto Sans Mono CJK / 思源等宽）以彻底消除 GPL 义务歧义；字体抽象为"字形提供者"接口，允许替换字体文件。
- 若坚持文泉驿：必须随包提供 GPLv2 全文与对应源码获取方式（About 页），并**删除**"运行时加载即规避 GPL"的表述（GPL v2 不区分静态嵌入与运行时加载，分发字体文件本身即触发义务）。
- 依 D8 决策，排版不依赖字体 advance，更换字体不影响分页正确性。

### D7 字体覆盖与 UTF-8 假设的冲突
- **位置**：§13、§6.2、§15
- §13 说字体"覆盖 GBK 全集"，§6.2 的断行却按 UTF-8 首字节判全角，§15 又说"混合编码不转换，按字节处理"。GBK 文本下字节 `0xE4–0xE9` 的含义与 UTF-8 完全不同 → 全角判定与字形映射都会错。
- 文档是否隐含"输入必须是 UTF-8"？若是，GBK 文件如何呈现（全部半角？乱码？拒绝打开并提示？）？若否，排版与字形查表如何做到编码无关？

`→ 结论：【自决】`
- 只保证 **UTF-8**（允许 BOM，BOM 跳过不显示），与 A13 用户结论（自建 UTF-8 解码器）一致。
- 非法序列输出替换字形（按半角宽渲染占位方框），不尝试 GBK 或其它编码。
- 导入时做一次快速校验：非法字节比例 > 1% 时用提示框书提示"该文件可能不是 UTF-8，将以替换字符显示"。

### D8 等宽性的实测确认
- **位置**：§13、§6.1
- "汉字宽度 = 西文宽度 × 2，字符宽度仅两种值"需要实测数据支撑：数字、标点、全角空格、制表符在 WenQuanYi Zen Hei Mono 中的 advance 是否严格落在两档？请给出一张"字符类别 → advance"的实测表，因为它直接决定断行结果与 §16 的"渲染结果确定性"。

`→ 结论：【自决】`
- **不依赖字体的 advance 等宽性**：排版宽度由分类表决定（全角 = 2 个半角列、半角 = 1 列、非法/其他 = 1 列替换字形），字形按所在网格列矩形缩放/居中绘制并裁剪。
- 因此实测表不再是排版正确性的前提（只影响观感）；文档改为记录"字形按网格约束绘制"与字体可替换。

### D9 性能指标的口径与最坏情况
- **位置**：§14、§5.3
- "定位任意行 < 0.1ms"是平均值还是最坏值？`locate()` 的最坏耗时**不由 K 约束**，而由**行长**决定：需要连续调用 `nextNewline` 最多 `K-1` 次，每次扫描一整行的字节。例如 1000 行 × 5KB 的文件，`K = 256`，最坏要扫约 1.27MB。
- "低端 ARM"未定义具体型号/主频/存储介质；"首次打开 5MB < 100ms"是否包含索引写盘？"常驻 < 35KB"是否包含字体 mmap 的 RSS（见 A8）？
- 建议把每条指标写成"场景 + 输入规模 + 统计口径（均值/95 分位/最坏）"。

`→ 结论：【自决】` 指标改为"场景 + 输入 + 口径"：
- 定位任意行：平均 ≤ 0.1ms（行平均长度 ≤ 128B）；**最坏 = O((K−1) × 区间最大行长)，不作保证**。
- 导入 5MB（扫描 + 建索引 + 写盘）：≤ 300ms，允许在提示框书显示进度。
- 二次打开（读索引 + ≤8KB 校验）：≤ 10ms。
- 翻页：下一页 ≤ 10ms，上一页 ≤ 20ms（V ≤ 40 行、行平均 ≤ 128B）。
- 内存：A8 用户已决定暂不做硬预算，此处仅作为调试页显示与回归测试的参考口径。

### D10 崩溃与中断恢复
- **位置**：§15
- 索引写到一半进程被杀 → 文件不完整（当前无校验和，见 A7）；下次打开如何判定并重建？是否需要"临时文件 + 原子替换"？进度文件同理（见 C8）。

`→ 结论：【自决】`
- 所有落盘（索引/进度/配置/书信息）统一 "tmp + rename"（C8）；打开时先校验魔数与 CRC32。
- 失败即按 C1/C6 的策略重建或重置，坏文件改名 `*.bad`，最多保留一份以避免占用空间。

### D11 可测试性与确定性验证
- **位置**：§16
- "渲染结果确定性 / 像素级一致"如何验证（黄金图像回归？跨 GPU 光栅化差异如何处理）？
- "翻页不重不漏"如何验证（逐页拼接输出与全文渲染做差分？随机翻页顺序的不动点测试）？
- 建议在文档中加入一张测试矩阵（输入类型 × 边界 × 期望）。

`→ 结论：【自决】` 测试矩阵（写入文档附录）：
1. **排版确定性**：同参数同输入 → 帧缓冲逐字节一致（软件渲染使跨设备可比）；黄金图像回归。
2. **翻页不重不漏**：把每页渲染的字节区间拼接，必须等于从页首锚点到文件尾的完整字节流；随机翻页顺序做不动点测试。
3. **边界语料**：空文件、单 `\n`、无 `\n` 的 5MB 单行、500 万连续 `\n`、超长行、`---` 在首/中/尾、`~~~` 未闭合、UTF-8 非法序列。
4. **存储**：CRC 篡改、截断、版本不匹配、写入中途 kill -9。
5. **恢复**：不同字号/边距/屏幕尺寸下，锚点必须落在同一源字节。

### D12 无障碍与系统级适配
- **位置**：全文缺失
- 纯自绘 UI 对 TalkBack / VoiceOver 不友好；系统字号缩放是否遵循？若明确不支持，请在文档中声明范围，避免后续被当作缺陷。

`→ 结论：【自决】`
- v1 明确**不支持** TalkBack / VoiceOver（自绘 UI），不跟随系统字号缩放（字号由应用内设置控制）；在文档中声明范围。
- 过渡方案（列入 backlog，不作 v1 承诺）：提供"导出当前页纯文本"的无障碍文本接口。
